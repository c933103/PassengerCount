# PassengerCount 1.11 — local upgrade-candidate provenance gate

## Status and scope (13 October 2026)

PR #13 is [merged](https://github.com/c933103/PassengerCount/pull/13). [Main run 38332107783](https://github.com/c933103/PassengerCount/actions/runs/38332107783) passed all host/browser/build checks and the complete installed **API 35** lifecycle suite. This does not sign or publish an upgrade. GitHub's CI key is disposable and **is not the original 1.10 update key**.

This gate checks a future *privately signed* 1.11 APK against a trusted, green CI aligned APK and the previously delivered 1.10 package. It checks exact package/version/SDK metadata, one signer with valid v2/v3 signatures and the same public certificate as delivered 1.10, exact per-entry APK payload continuity from CI (including resources, manifest and dex), and every packaged web/data/vendor asset against a clean, exact-source checkout. It cannot prove the physical signing computer is uncompromised, nor that original private keys are safe. It makes **no** network requests, does not require or read the keystore, and does not publish.

## Private release-machine procedure

Prerequisites: trusted Python 3, git, Java and official Android SDK Build Tools 35.0.0; clean checkout of **exact** accepted green source; verified original delivered 1.10 APK; accepted run's `aligned.apk`; original private keystore **kept entirely off GitHub and this chat**.

1. Independently verify the accepted workflow run head, source commit and artifact ZIP SHA-256, then extract `aligned.apk`. Keep it outside the source checkout. Confirm its own SHA-256 against the accepted value.
2. On the private machine only, sign **that** `aligned.apk` using the original retained key, for example:

   ```bash
   # SIGNING_KEYSTORE, SIGNING_STORE_PASSWORD, SIGNING_KEY_PASSWORD and
   # SIGNING_KEY_ALIAS exist only on the private signing host.
   "$ANDROID_HOME/build-tools/35.0.0/apksigner" sign \
     --min-sdk-version 26 \
     --v1-signing-enabled false --v2-signing-enabled true --v3-signing-enabled true \
     --ks "$SIGNING_KEYSTORE" --ks-key-alias "$SIGNING_KEY_ALIAS" \
     --ks-pass env:SIGNING_STORE_PASSWORD --key-pass env:SIGNING_KEY_PASSWORD \
     --out "$PRIVATE_OUTPUT/PassengerCount-1.11.apk" \
     "$ACCEPTED_CI/aligned.apk"
   ```

3. Run the **separate** read-only verifier. The script path may be from a newer docs/tools checkout, but `--source-dir` must point to the clean checkout at exactly the source commit of the aligned APK:

   ```bash
   python3 scripts/verify-release-candidate.py \
     --source-dir "$ACCEPTED_SOURCE" \
     --candidate "$PRIVATE_OUTPUT/PassengerCount-1.11.apk" \
     --aligned-apk "$ACCEPTED_CI/aligned.apk" \
     --previous-apk "$DELIVERED_110/PassengerCount-1.10.apk" \
     --expected-source-commit ed0a10a8bd61f9be7348cf6e3b980013acdecad3 \
     --expected-aligned-sha256 c39e95233fa795f1af3e0f8f920933835ccb5a77ee31bb4568611fa15478e7f3 \
     --android-sdk "$ANDROID_HOME"
   ```

   The executable fails closed with `RELEASE_CANDIDATE_REJECTED` on any mismatch. A pass prints only public hashes and a local candidate-verification receipt. Never upload keystores, signing passwords or files containing private key material to CI, PRs or chat. Never replace the accepted source with a different revision while reusing the same aligned hash.

4. Separately perform an **actual same-package upgrade from signed 1.10/code11 to signed 1.11/code12 without clearing app data**, and verify records, journal resumes, uploaded receipt persistence, corrections, export and deletion. Test a fresh install too.
5. Keep the **PC-DEVICE** field checklist and explicit Android permission revocation/background start behavior as remaining release checks. API 35 emulator passes do not establish API 26/Android 8–9 storage-provider behavior, actual carrier/GPS field behavior, live backend upload or power-loss consistency.
6. Only after those checks and explicit publication approval, record final source/run, both APK hashes, signing certificate, installed upgrade results and GitHub tag/release URL. A locally verified APK does **not** mean release 1.11 was published.

### Regression check (safe in regular CI)

Run `python3 -m unittest discover -s tests -p 'release_candidate_test.py' -v`. The 12 tests use temporary synthetic APKs and deliberately **mock** `aapt2` and `apksigner` to test verifier logic and refusal behavior. They never validate a real production signature and must never be counted as evidence of original-signer acceptance. The live signer comparison always uses real Android SDK tools on the private release host.

## Source restrictions

This change does not edit application runtime, manifest, packaged assets, versionCode or signing material; it adds local release verification and current project status only. PR #13's exact main API 35 acceptance remains separate from the release gate and required field-device acceptance.
