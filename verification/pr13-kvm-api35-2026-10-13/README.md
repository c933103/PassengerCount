# PR #13 — accelerated API35 installed acceptance

## Root cause and runner configuration

Run [38131702284](https://github.com/c933103/PassengerCount/actions/runs/38131702284) executed the host tests, production APK build and instrumentation compilation on GitHub-hosted Ubuntu 24.04.5. The existing installed runner refused at its unchanged `/dev/kvm` read/write check (exit 2), before emulator creation. The prior log does not prove whether the KVM character device was absent or just inaccessible.

GitHub documents accelerated Android SDK tools on GitHub-hosted Linux runners and the need to grant KVM access: [GitHub Linux runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [GitHub's Android virtualization announcement](https://github.blog/changelog/2024-04-02-github-actions-hardware-accelerated-android-virtualization-now-available/). The pinned runner is `ubuntu-24.04` (x64, full hosted VM; **not** `ubuntu-slim`). Ubuntu's hosted image lists `acl` as installed.

Immediately before the required installed stage, the workflow writes `kvm-access.txt` into the always-uploaded `PassengerCount-API35-lifecycle-*` evidence artifact. It classifies missing device vs unsupported runner vs denied permissions; if the genuine character device exists but is inaccessible, it grants **only the ephemeral job user** an ACL using `sudo -n setfacl -m u:<user>:rw /dev/kvm`. It never globally changes modes, changes udev rules, manufactures a KVM device or uses software emulation. The original `test-android-installed.sh` `-r && -w` preflight and `emulator -accel-check` remain mandatory.

## Follow-up: emulator dynamic library after KVM permission fix

[Run 38318168810](https://github.com/c933103/PassengerCount/actions/runs/38318168810) confirmed that `/dev/kvm` **exists** (`root:kvm`, mode 0660), but the GitHub-hosted `runner` lacked access. The ACL grant to `runner` succeeded, without changing the global file mode. The job then exited **127 before any emulator or installed instrumentation execution**, because the newly downloaded Android emulator's QEMU binary could not load `libpulse.so.0`. This exact stderr is preserved in [the uploaded evidence artifact](https://github.com/c933103/PassengerCount/actions/runs/38318168810/artifacts/11777853022), under `emulator-version.txt`.

The workflow now installs Ubuntu 24.04's `libpulse0` distro package on the disposable hosted runner (only when missing) and verifies the loader mapping. Headless `-no-audio` does not eliminate this dynamic-loader requirement. New artifact `emulator-dependency.txt` documents package availability. The emulator-version and mandatory `-accel-check` failures now print their captured output to the job console, retain exit-2 blockers and never fall back to unaccelerated emulation. This addresses an additional **runner dependency**, not an app defect. All installed API35 assertions still require actual execution.

## WebView fixture root-cause evidence and correction

[Workflow #38319133449](https://github.com/c933103/PassengerCount/actions/runs/38319133449), [API35 installed evidence](https://github.com/c933103/PassengerCount/actions/runs/38319133449/artifacts/11777019803): the emulator successfully booted and KVM acceleration was confirmed. The bootstrap Java instrumentation did run, but test-only `WebView` ended at `chrome-error://chromewebdata/` with `fixtureStage=not-started` and a 45-second timeout; it never evaluated the fixture modules or exercised app behavior. The prior client returned HTTP 403 for *every* intercepted resource, potentially including the synthetic document created by `loadDataWithBaseURL`; this is a test harness navigation defect, not proof of a production defect. Android's WebView docs support serving secure-origin local pages via `shouldInterceptRequest` instead of opaque `file:` or `data:` origins.

The test-only harness now loads the **exact** local fixture URL `https://appassets.androidplatform.net/fixture.html` and serves its immutable in-memory HTML from `shouldInterceptRequest`. No other URL is allowed: unexpected requests receive 403, increment the required zero-network-request assertion, and appear in the test log. `setBlockNetworkLoads(true)` stays enabled, as does the real production JavaScript bridge. Navigation/resource-error and module-console diagnostics are retained. The fix needs an observed full API35 run before acceptance; do not infer success from code review alone.

## Browser-generated icon during installed bootstrap

[Workflow #38319687384](https://github.com/c933103/PassengerCount/actions/runs/38319687384), [installed API35 evidence](https://github.com/c933103/PassengerCount/actions/runs/38319687384/artifacts/11779005385): the new local fixture document **successfully loaded**, production modules and cached local catalogue initialized, and the native workspace/preference commits passed. Bootstrap's final strict zero-unexpected-network-request assertion failed solely because the Android WebView automatically requested same-origin `/favicon.ico`, which the fixture had not provided (log `TEST_BLOCKED_RESOURCE`). No subsequent phases ran.

Now the test-only fixture **explicitly links** to the favicon and serves only that exact path as a tiny, bundled in-memory PNG; its bytes are not downloaded and no connection is opened. Every other unexpected URL still receives HTTP 403 and increments `interceptedRequests`, and `setBlockNetworkLoads(true)` remains enabled. The test still requires zero unexpected resource requests and all original installed lifecycle phases; this is not a bypass of network safety or test requirements.

## Additional installed test assertions

The existing production APK, signed test APK, native foreground-service lifecycle, real GPS callbacks, SIGKILL-and-system-restart and native deletion tests remain present. Three new required, cold-process instrumentation phases (`receipts-prepare`, `receipts-recover`, `receipts-final`) exercise production `storage.js`, the exact JNI/Android storage bridge and the production `record-deletion.js` coordinator using *synthetic local receipt state*. They verify immutable completed-upload identity, persistence across edits, an unconfirmed receipt remaining uncertain, exact deletion of a selected journal and preservation of the unrelated completed receipt across **two actual Android process restarts**. No live network or backend write is attempted or claimed. These phases do not claim to test full interactive UI Undo/Redo or a real server upload, which are separately exercised by host/browser tests.

## Acceptance rule

A successful build, 295 Node tests and hosted browser checks do **not** substitute for installed API35 results. Require observed `PHASE_PASS` and `INSTRUMENTATION_CODE: -1` for **all** phases, genuine API35 fingerprint/SDK, acceleration evidence, native traces and overall green workflow on the updated PR head. Classify KVM prerequisite failure as runner environment, instrumentation exceptions as app/test defects, and remain draft/unmerged until validated. API26, physical device, power loss, original production signer and server idempotency are not covered.

## Reproduction

Push the current PR branch; trigger `Validate Android v1.11` via normal pull-request CI on Ubuntu 24.04. Evidence is uploaded by `Preserve installed lifecycle evidence` even if KVM access fails. Do not ignore the preflight or promote APK artifacts from failed runs.
